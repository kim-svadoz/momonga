# 원본 컴퓨터에서 이어서 할 일

채널 × 목적 구조(2026-10-27)는 영상 원본(`output/`)이 없는 컴퓨터에서 만들었다. 그래서 원본이 있어야 확인할 수 있는 부분이 남아 있다.

**`output/`과 부크크 명조·Pretendard·Yoon 글꼴이 있는 컴퓨터에서 이 저장소를 처음 pull하면, Claude는 이 문서를 읽고 아래 순서로 진행할지 사용자에게 먼저 제안한다.** 제안 없이 시작하지 않는다.

## 이 컴퓨터에서 확인한 것

| 확인한 것 | 방법 |
| --- | --- |
| 채널 + 목적 조합이 항상 같은 순서로 조립된다 | `python3 -m unittest tools/compose/test_compose.py` |
| 옛 스킬 3개와 피드백 45건이 새 위치에 빠짐없이 있다 | `python3 -m unittest tools/migration/test_rule_map.py` |
| `reel.swift`가 프로필·회차 파일을 읽고, 프로필이 다르면 결과가 다르다 | `bash tools/haul-reel/test_profile_swap.sh` |
| `reel.swift` 수정 전후 썸네일·자막 파일이 바이트까지 같다 | 위 스크립트 5번 (시험용 영상 + 시스템 글꼴) |
| 브라우저 편집기가 프로필을 읽는다 | `node --test apps/shorts-editor/test_profile.mjs` |

## 이 컴퓨터에서 확인하지 못한 것 (미검증)

1. **진짜 글꼴로 그린 결과.** 시험은 글꼴 이름을 시스템 글꼴로 바꿔서 돌렸다. 부크크 명조·Pretendard·Yoon으로 그린 썸네일과 자막이 수정 전과 같은지는 보지 못했다.
2. **`haul`(하울 릴스) 양식.** `channels/insta-reels/profile.json`의 `haul` 값은 `tools/haul-reel/README.md`의 옛 표를 옮겨 적었고, 한 번도 그려 보지 않았다. 돈키호테 1·2탄 결과와 같은지 모른다.
3. **실제 원본 영상.** 아이폰 4K 세로 원본(회전 정보 포함)으로 돌린 적이 없다. 시험용 영상은 540×960이다.
4. **효과음(`SFX=capcut`).** `assets/sfx/`가 없어서 한 번도 돌리지 못했다.
5. **사람 오려내기(`VIDEO_LOGO`, `THUMB_LOGO`).** 시험용 영상에는 사람이 없어서 해당 경로가 실제로 쓰이지 않았다.
6. **블로그·쓰레드 이관의 실제 사용.** 규칙이 빠짐없이 옮겨졌는지는 문장 대조로만 확인했다. 실제 글을 이 구조로 써 본 적은 없다.
7. **MP4 화면.** 시험용 영상에서 수정 전후 프레임 차이가 인코더 잡음 수준(0.5 이하)이었다. 진짜 영상에서는 보지 않았다.

## 순서

원본 컴퓨터에서 처음 pull한 뒤:

1. 이 컴퓨터에서 sugo를 쓴다면 `sugo:add`로 등록한다 (`sugo/config.json`은 컴퓨터마다 달라서 git에 없다).
2. 글꼴 확인: 부크크 명조·Pretendard·Yoon 초록우산어린이가 `~/Library/Fonts/`에 있는지 본다. 효과음은 `assets/sfx/`.
3. 시험을 진짜 글꼴로 돌린다.
   ```
   REEL_REAL_FONTS=1 bash tools/haul-reel/test_profile_swap.sh
   ```
   5번 비교가 통과하면 위 미검증 1번이 풀린다.
4. 지난 회차를 회차 파일로 옮긴다. 대상은 `output/261025/` 아래의 돈키호테 1탄·2탄 `reel_<회차>.swift`다.
   - 파일 맨 위의 `let` 값과 `caps` 배열을 `tools/haul-reel/episodes/<회차>.json`으로 옮긴다. 형식은 `channels/profile-schema.md`의 "회차 파일이 가지는 것". `tools/haul-reel/episodes/sample.json`(자라 맨즈 아우터)이 예시다.
   - 양식은 `haul`. 영상마다 바뀌는 글자(맨 위 라벨 "돈키호테 쇼핑템 N탄" 등)는 `overrides`에 둔다.
5. 옮긴 회차를 새 `reel.swift`로 다시 렌더하고 이전 결과와 비교한다.
   ```
   EPISODE=tools/haul-reel/episodes/<회차>.json swift tools/haul-reel/reel.swift <원본.MOV> <새 폴더>
   ```
   - 썸네일 JPG와 자막 SRT 4개는 이전 결과와 바이트까지 같아야 한다.
   - MP4는 인코더 때문에 바이트가 매번 달라진다. 장면 몇 곳(오프닝, 자막 구간, 엔딩)을 뽑아서 눈으로 본다.
   - 다르면 `haul` 양식 값(`profile.json`)을 고친다. 이때 미검증 2번이 풀린다.
6. 블로그·쓰레드 글을 새 구조로 써 본다: "쓰레드 글을 네이버 블로그로 옮겨줘"처럼 요청하고 `python3 tools/compose/compose.py naver-blog convert --brief ...` 로 조립된 안내문대로 진행되는지 본다.
7. 위가 모두 통과하면 사용자에게 **옛 스킬을 지울지** 묻는다. 대상: `naver-blog`, `threads-post`, `fashion-reels`, `blog-post`, `blog-to-reels`, `insta-post`, `shortform`.
   - 지우기 전에 `tools/migration/rule_map.md`의 "옛 스킬과 새 채널 문서가 같은 내용을 갖는 기간"을 읽는다.
   - 지운 뒤에는 `tools/migration/test_rule_map.py`가 옛 파일을 git 기록(`a42526e`)에서 읽으므로 계속 통과한다.
8. 끝나면 이 문서의 "미검증"에서 풀린 항목을 지우고 날짜를 적는다.

## 알려진 한계

- `reel.swift`의 자막 종류별 글꼴(꼬리표, 가격, 강조 등)은 아직 코드 안에 있다. 프로필의 `fonts`는 훅 큰 제목, 메인 자막, 엔딩, 덧말에만 적용된다.
- 채널 5개(인스타 게시물·스토리, 틱톡, 유튜브 쇼츠·롱폼)는 규격 칸이 `⬜`다. 공식 문서로 확인한 뒤에 채운다.
- 롱폼 전용 편집 모듈이 필요한지는 정하지 않았다.
- 옛 스킬과 `channel.md`가 같은 규칙을 갖는 동안은 `channel.md`를 기준으로 고친다.
- 브라우저 편집기는 효과음 규칙과 훅 위치를 프로필에서 읽지 않는다. 화면 비율, 길이 상한, 안전 영역만 읽는다.
- `python3 tools/compose/compose.py insta-reels edit`의 출력은 약 35KB다. 피드백이 쌓이면 더 커진다.
